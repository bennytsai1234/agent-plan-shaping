# Agent Plan Shaping

一份給 AI coding agent 的全域方案塑形指示。

它處理的不是「模型會不會照方案實作」，而是更前面的問題：**模型如何把廣泛思考壓縮成可執行方案。**

很多 coding agent 在方案形成階段會自然追求完整、健壯、主動、可擴充與最佳實務。這些傾向本身未必有錯，但如果每一個想到的改善、風險或未來可能性都直接取得「方案資格」，後續實作即使完全正確，也可能把專案穩定地蓋在一個過度複雜的藍圖上。

這份指示採用的核心方法不是壓制這些傾向，而是**重新規定它們的出口**：

> 允許模型想得很廣，但只有完成目前已確認需求所必需的內容，才有資格進入可執行方案。

額外的周到、風險意識與改善衝動，可以用來檢驗方案；真正值得讓使用者知道、但不屬於目前方案的內容，可以進入沒有執行權的「旁註」。

## 使用方式

將 [`AGENTS.md`](./AGENTS.md) 作為 coding agent 的全域指示，放在方案討論與工程規範之前生效。

它適合與其他工程規範疊加使用：

```text
使用者需求
    ↓
方案塑形（本 repo）
    ↓
工程／協作規範
    ↓
已確認方案
    ↓
實作
```

這一層只負責「什麼東西有資格成為方案」，不替代個別專案的工程規範。

## 核心原則

- 思考內容與方案內容是兩個不同集合。
- 「想到」不等於「應該做」。
- 想做更多時，先用它挑戰目前的簡單方案，而不是直接擴張方案。
- 分析可以很細，產品與實作只保留目前有行為差異的複雜度。
- 方案預設採用最小充分模型。
- 方案外但值得知道的內容，可以進入旁註；旁註沒有執行權。
- 使用者未反對旁註，不代表旁註被接受。
- 進入執行後，以使用者已確認的方案為契約。
- 不為方案外想法額外消耗工具呼叫、修改、測試與探索成本。

## 背景

這份指示來自一個實際問題：模型在 coding 階段往往能非常忠實地執行既定方案，真正高風險的地方反而是方案形成階段。如果前期藍圖加入了不必要的 state、abstraction、fallback、未來擴充或治理機制，後面的功能會持續建立在這些前提上，專案複雜度因此逐步固化。

因此，本 repo 的目標是改善方案形成的「投影函數」：

> **讓模型保留廣泛思考與助人傾向，但重新定義什麼內容有資格成為可執行方案。**
